# RP2040 / Raspberry Pi Pico support

PlatformIO environment: `rpipico`, board ID `pico`, Arduino framework using the Earle Philhower Arduino-Pico core. The current PlatformIO board documentation identifies the `raspberrypi` platform and `pico` board ID; the Arduino-Pico PlatformIO guide documents selecting the Earle Philhower core via `board_build.core = earlephilhower`.

```bash
pio run -e rpipico
pio run -e rpipico -t upload
pio device monitor -b 115200
```

Default pin assignments are examples only. Confirm the exact board and external target voltage levels before wiring. Select exactly one interface with `NEXUS_LINK_MODE`:

- `1`: UART, `Serial1` (default RX GPIO 5 / TX GPIO 4)
- `2`: SPI (default SCK 18, MISO 16, MOSI 19, CS 17)
- `3`: I²C (default SDA 8, SCL 9, address 0x42)

The firmware defaults to disarmed; both `NEXUS_AUTHORIZED_LAB_TARGET` and `NEXUS_ACTIVE_FUZZ_ENABLED` are `0`. The Pico runner is a cooperative loop. It does not claim to run the ESP32 FreeRTOS dual-task architecture.

RP2040 is Cortex-M0+. The optional sample target hook in `examples/target_hooks/rp2040_hardfault_capture.cpp` retains the exception-stacked R0-R3, R12, LR, PC, xPSR, MSP/PSP-derived stack pointer, EXC_RETURN and ICSR in `.noinit` memory. It deliberately does not report CFSR/BFAR: Cortex-M0+ does not implement the Cortex-M3/M4 configurable fault-status register set. The target hook must be integrated into the test firmware and `nexus_rp2040_print_fault_snapshot()` called after a controlled reset. A debugger/SWD probe can also inspect the retained memory directly.

For separate target panic UART capture when the Pico is using its hardware UART for fuzz traffic, use a second host USB-UART adapter. Keep target debug output electrically and logically separate from the fuzz bus.
